# Line Dominance System (LDS)
## Mathematical, Vector, and Resolution Specification

**Audience**: Gameplay / systems programmer

**Purpose**: This document defines the *exact mathematical model* behind Line Dominance Score (LDS). It is intended for implementation, debugging, and balancing. It deliberately ignores player-facing explanations, UI, animation, or narrative framing.

---

## 1. Coordinate System

### 1.1 Grid Coordinates

The 3×3 grid is mapped to 2D integer coordinates:

```
Grid index → (x, y)

1 → (-1,  1)
2 → ( 0,  1)
3 → ( 1,  1)
4 → (-1,  0)
5 → ( 0,  0)
6 → ( 1,  0)
7 → (-1, -1)
8 → ( 0, -1)
9 → ( 1, -1)
```

Opponent bodies are assumed centered at (0, 0).

---

## 2. Weapon Movement Vectors

### 2.1 Path Definition

A weapon movement is defined as:

```
Movement = {
  start_cell ∈ [1..9],
  end_cell   ∈ [1..9]
}
```

Convert to coordinates:

```
start = coord[start_cell]
end   = coord[end_cell]
```

The movement vector:

```
V = end - start
```

If `V = (0,0)`, treat as a thrust vector `(0, sign)` toward opponent center.

---

## 3. Discrete Path Sampling

### 3.1 Path Cells

For collision and timing purposes, the path is discretized:

```
path = Bresenham(start, end)
```

This yields an ordered list of cells:

```
path = [p0 = start, p1, p2, ..., pn = end]
```

---

## 4. Contact Detection

### 4.1 Intersection Set

Given two paths `path_A` and `path_B`:

```
I = path_A ∩ path_B
```

If `I = ∅`, no blade contact occurs.

### 4.2 Steps to Contact

For each actor:

```
steps_to_contact = min { i | path[i] ∈ I }
```

This value is critical for timing resolution.

---

## 5. TimingComponent (TC)

### 5.1 Inputs

- AP_pre        : Action Points committed before INDES
- AP_post       : Action Points committed after INDES
- FP_spent      : Focus Points spent
- speed         : Character speed scalar (> 0)
- steps_to_contact

### 5.2 Effective Commitment

```
AP_eff = AP_pre + 0.5 * AP_post

TimePower = (AP_eff + FP_spent * FP_WEIGHT) * speed
```

### 5.3 Reach Score

```
if steps_to_contact == 0:
    reach = TimePower * CONTACT_BONUS
else:
    reach = TimePower / steps_to_contact
```

### 5.4 Normalization

```
TimingComponent = clamp(reach / TIMING_NORM, 0, 1)
```

---

## 6. PositionComponent (PC)

### 6.1 Guard Alignment

Compute the primary direction of movement:

```
V_norm = normalize(V)
```

Define guard facing vector `G` as normalized vector from origin to `start`:

```
G = normalize(start)
```

Alignment is dot product:

```
alignment = dot(G, V_norm)
```

### 6.2 Distance Penalty

```
path_length = len(path) - 1

penalty = DIST_COEFF * (steps_to_contact / path_length)
```

### 6.3 Position Score

```
PositionComponent = clamp(alignment - penalty, PC_MIN, PC_MAX)
```

---

## 7. AngleComponent (AC)

### 7.1 Vector Angle

Given vectors `V_A` and `V_B`:

```
φ = arccos( dot(normalize(V_A), normalize(V_B)) )
```

Angle is in radians.

### 7.2 Angle Bands

| Condition | Description | Modifier |
|--------|-------------|----------|
| φ ≥ 3π/4 | Opposing lines | +AC_OPPOSE |
| π/3 ≤ φ < 3π/4 | Crossing | +AC_CROSS to earlier arrival |
| φ < π/4 | Aligned | −AC_ALIGN |

Earlier arrival is determined via TimingComponent.

---

## 8. StructureComponent (SC)

Structure represents blade mechanics and follow-through.

### 8.1 Structural Modifiers

Additive modifiers (examples):

- Thrust toward centerline: `+SC_THRUST`
- Long-edge alignment: `+SC_EDGE`
- End cell adjacent to opponent center (5): `+SC_PRESSURE`
- Ending on outer flank (1,3,7,9): `−SC_EXPOSE`

### 8.2 Structure Score

```
StructureComponent = clamp(sum(modifiers), SC_MIN, SC_MAX)
```

---

## 9. Line Dominance Score (LDS)

```
LDS = w_T * TimingComponent
    + w_P * PositionComponent
    + w_A * AngleComponent
    + w_S * StructureComponent
```

Weights default to:

```
w_T = 0.45
w_P = 0.20
w_A = 0.20
w_S = 0.15
```

(Subject to tuning.)

---

## 10. Differential Resolution

For two actors A and B:

```
Δ = LDS_A - LDS_B
```

Thresholds:

```
Δ ≥ HIT_T      → Dominant
|Δ| ≤ NEUTRAL  → Contested
Δ ≤ −LOSS_T    → Dominated
```

These thresholds are interpreted differently depending on **intent** (defined in the core spec).

---

## 11. Determinism & Debugging

- All calculations are deterministic given inputs.
- Floating point precision should be clamped consistently.
- Debug mode should log:
  - Paths
  - Intersection
  - Each LDS component
  - Final Δ

---

## 12. Balancing Notes

- TimingComponent dominates outcomes; reduce `FP_WEIGHT` if Focus feels mandatory.
- PositionComponent punishes poor guard discipline.
- AngleComponent controls bind frequency.
- StructureComponent defines follow-up quality, not win probability.
